
# Pull request security and workflow separation

WeighIn uses two GitHub Actions workflows to separate **untrusted benchmark execution** from **privileged pull request commenting**:

1. `weighin.yml` runs the benchmark for a pull request and uploads its report and metadata.
2. `weighin-comment.yml` runs after the producer workflow completes, downloads its artifacts, validates them, and posts or updates the pull request comment.

This is intentional. A single workflow that executes pull request code and also has permission to write pull request comments would combine two different trust levels in one job.

## Why a benchmark workflow must not have write permissions

A pull request can come from a fork controlled by someone who does not have write access to the base repository.

The pull request may change more than application source files. It can also change:

- Build scripts and package lifecycle scripts.
- Test commands and dependencies.
- GitHub Actions workflow files.
- Contract fixtures and configuration files.
- Files consumed by tools during the benchmark.

Executing these files means executing code supplied by the pull request author.

If that code runs in a job with a write-capable `GITHUB_TOKEN`, it may be able to use the token's permissions to modify repository resources. If secrets are available to the job, malicious code may also attempt to expose them.

This is the class of vulnerability commonly called a **pwn request**: untrusted pull request code is executed in a privileged workflow context.

The benchmark producer should therefore use the ordinary `pull_request` event and the minimum permissions it needs:

```yaml
name: WeighIn Benchmark

on:
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  benchmark:
    runs-on: ubuntu-latest
    steps:
      # Checkout and benchmark setup go here.
      # Do not grant pull-requests: write to this job.
      # Do not expose repository secrets to untrusted benchmark code.
```

The repository's example producer workflow uses read-only repository access. It builds and measures the pull request revision, then uploads the report and metadata. It does not need permission to create a pull request comment.

## Why the comment workflow uses `workflow_run`

The comment workflow is triggered by the completion of the benchmark workflow:

```yaml
name: WeighIn Comment

on:
  workflow_run:
    workflows: ["WeighIn Benchmark"]
    types:
      - completed
```

A `workflow_run` workflow is defined on the default branch and executes in the base repository's trusted workflow context. This makes it suitable for a narrowly scoped follow-up action that needs permission to comment.

The important security property is not simply the event name. It is what the privileged workflow does and does not do.

The comment workflow must:

- Use the trusted workflow definition from the base repository.
- Download the artifact belonging to the completed producer run.
- Treat every downloaded artifact as untrusted input.
- Validate the report and metadata before making an API mutation.
- Never check out, build, install dependencies from, or execute pull request code.
- Use only the permissions required to read the artifact and update a pull request comment.

A `workflow_run` workflow is **not automatically safe**. Downloading an artifact from an untrusted run and executing a script from that artifact would reintroduce the same class of vulnerability.

## Current privilege boundary

The repository's example consumer workflow declares:

```yaml
jobs:
  post-comment:
    runs-on: ubuntu-latest
    if: >-
      github.event.workflow_run.conclusion == 'success' &&
      github.event.workflow_run.event == 'pull_request'
    permissions:
      pull-requests: write
      actions: read
```

These permissions serve separate purposes:

| Permission | Purpose |
|---|---|
| `actions: read` | Download the artifact associated with the producer workflow run. |
| `pull-requests: write` | Create or update the WeighIn report comment. |

Do not add `contents: write`, `issues: write`, or other permissions unless a separately reviewed feature requires them.

The current consumer only runs the comment step after a successful pull request producer. A failed benchmark or policy check still leaves its uploaded report available as a workflow artifact, but does not automatically post a comment through this example consumer.

## Artifact validation before commenting

Artifacts downloaded by a `workflow_run` workflow must be treated as untrusted data. A pull request author may influence the report generated by the producer, and the consumer must not assume that an artifact is trustworthy merely because GitHub Actions uploaded it.

The current comment consumer performs the following checks before creating or updating a comment:

### 1. Required files

The consumer requires both the report file and the PR metadata file to exist.

### 2. Report structure

The report must:

- Contain non-whitespace content.
- Include the expected `<!-- weighin-report -->` marker.
- Include the expected `WeighIn Benchmark Report` heading.

A missing or malformed report is rejected.

### 3. Versioned metadata

The metadata parser requires valid JSON with:

- `schemaVersion` equal to the supported schema version.
- A non-empty repository name matching the trusted base repository.
- A positive integer pull request number.
- A 40-character hexadecimal commit SHA.

Legacy unversioned metadata and unsupported schema versions are rejected.

Example metadata:

```json
{
  "schemaVersion": 1,
  "repository": "WeighInNG/WeighIn",
  "prNumber": 27,
  "headSha": "f679238a096b49df0edfaf7d02d5bfa2dfd6be8f"
}
```

The repository field identifies the base repository that owns the trusted comment workflow, including when the pull request originates from a fork.

### 4. Producer and metadata revision consistency

The consumer compares the producer workflow's `head_sha` with the SHA recorded in the metadata.

The metadata SHA must either equal the producer SHA or identify a merge commit whose parent includes the producer SHA. This accounts for the synthetic merge commit that can be checked out by a `pull_request` workflow.

### 5. Current pull request freshness

The consumer reads the current pull request head from GitHub and compares it with the producer revision.

If the pull request has advanced since the benchmark ran, the report is stale. The consumer skips the comment update and reports the reason in the workflow warning and job summary.

This prevents an older workflow run that finishes late from overwriting a report for a newer commit.

### 6. No artifact execution

The consumer reads the report and metadata as data. It does not run scripts, install packages, build contracts, or execute files from the downloaded artifact.

The report is Markdown generated by the WeighIn reporting path. The consumer checks its expected structure before submitting it to GitHub. GitHub renders comments using its Markdown/HTML sanitization; this structural check should not be mistaken for a general-purpose sanitizer for arbitrary user-supplied Markdown.

## Why not use `pull_request_target` for the benchmark?

`pull_request_target` runs with the base repository's trust and permissions. It is useful for certain metadata-only tasks, but it becomes dangerous when the workflow checks out and executes code from the pull request.

For example, this is unsafe:

```yaml
# DO NOT USE THIS PATTERN.
on:
  pull_request_target:

jobs:
  benchmark:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha }}

      - run: npm install
      - run: npm test
```

The checkout makes the pull request's files available to the job. The subsequent commands can execute attacker-controlled scripts while the job has access to the privileged token and secrets.

WeighIn does not need this arrangement. The ordinary `pull_request` producer can benchmark with read-only permissions, and the separate `workflow_run` consumer can post the result without executing the pull request's code.

## Security checklist for maintainers

Before changing either workflow, verify that:

- [ ] The producer remains on `pull_request` for pull request benchmarks.
- [ ] The producer token remains read-only.
- [ ] The producer does not receive secrets it does not need.
- [ ] The consumer is defined on the base repository's default branch.
- [ ] The consumer is triggered only by the intended producer workflow.
- [ ] The consumer uses the producer run ID when downloading artifacts.
- [ ] The consumer does not check out or execute pull request code.
- [ ] Metadata is validated against the trusted repository and producer run.
- [ ] Stale reports are skipped.
- [ ] The consumer has only the permissions needed for artifact reading and commenting.
- [ ] Action dependencies are pinned to reviewed immutable revisions.
